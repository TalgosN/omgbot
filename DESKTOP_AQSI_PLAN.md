# Виарыч: обсуждение режима ПК и интеграции расходников с aQsi

Зафиксировано: 30.10.2026.
Статус: обсуждение отложено; реализация не начата, предложения не согласованы окончательно.

## Цель

Сделать приложение удобнее на компьютере и убрать повторный ввод приёмок и инвентаризаций напитков в aQsi и Виарыче.

## 1. Открытие на компьютере

Пользователи работают в Telegram Desktop и Telegram в браузере. Сейчас приложение открывается небольшим окном, которое приходится растягивать вручную. Запрос: открывать его максимально развёрнутым.

По результатам предыдущего изучения кода большинство страниц вызывает `expand()`, а запрос настоящего полноэкранного режима используется отдельно в сценарии камеры. Также страницы имеют ограничения ширины содержимого.

Предложено:

- Для ПК запрашивать полноэкранный режим, если его поддерживает клиент Telegram.
- Предусмотреть обычное окно, если клиент отклонит запрос полноэкранного режима.
- Адаптировать ширину и расположение элементов для большого экрана.
- На телефоне сохранить удобную мобильную компоновку и существующую навигацию.

Поддержку и поведение нужно проверить отдельно в Telegram Desktop и Telegram Web. Автоматическое разворачивание на каждом клиенте пока не подтверждено.

## 2. Возврат на главную

Пользователь подтвердил: речь о главной странице приложения, не о меню бота.

Запрос: обеспечить заметный возврат из модулей на главную, чтобы на ПК можно было переходить между модулями без свайпов.

Предложено:

- На основных страницах модулей — кнопка «⌂ Главная».
- Во вложенных разделах, формах и карточках — «← Назад» на предыдущий уровень.

## 3. Приёмка напитков: aQsi → Виарыч

### Как работают сейчас

При поступлении напитков приёмку всегда оформляют в личном кабинете aQsi: указывают товары, количества, закупочные цены и другие сведения. Те же поступления приходится отдельно учитывать в расходниках Виарыча.

aQsi рассчитывает остатки с учётом поступлений и продаж через кассу.

### Что требуется

Получать из aQsi факт приёмки и состав документа, чтобы не вводить поступление повторно в Виарыче.

### Предложенный процесс

1. Приёмку оформляют и проводят в aQsi.
2. Виарыч получает документ и его позиции.
3. Определяет клуб и сопоставляет товары с каталогом расходников.
4. Учитывает поступление и сохраняет связь с исходным документом.

При реализации нужно обеспечить однократную обработку документа, обработку несопоставленных товаров и согласовать поведение при изменении или отмене приёмки. Частоту получения документов пока не выбирали.

### Открытый вопрос об остатках

Перенос одних приёмок не учитывает продажи через кассу. Независимый остаток в Виарыче в таком случае может расходиться с aQsi.

Предложено показывать для напитков:

- «По учёту aQsi» — расчётный остаток из aQsi.
- «Последний пересчёт» — фактическое количество, дата и сотрудник.
- Приёмки — в истории поступлений.

Этот вариант ещё не подтверждён пользователем. Нужно согласовать, импортируем ли приёмки с изменением локального остатка или используем aQsi как источник расчётных остатков. Нельзя одновременно прибавлять приёмку к локальному остатку и заменять его балансом aQsi без согласованной логики.

## 4. Инвентаризация: Виарыч → aQsi → результат

### Что требуется

Сотрудники пересчитывают напитки и вводят фактические количества в Виарыче. Результат передаётся в aQsi как инвентаризация, чтобы не оформлять её повторно вручную. После обработки Виарыч получает итог с расхождениями.

По описанию текущего процесса пользователя, после утверждения инвентаризации aQsi принимает фактические остатки и показывает расхождения по количеству и сумме.

### Предложенный процесс

1. Сотрудник запускает отдельный «Пересчёт напитков» в расходниках.
2. Вводит фактическое количество по позициям.
3. Завершает пересчёт целиком; один пересчёт соответствует одному документу.
4. Видит предварительное сравнение: учётный остаток / факт / разница.
5. После подтверждения документ отправляется в aQsi.
6. Виарыч проверяет результат обработки и показывает номер документа, статус и расхождения.

Предложено не отправлять отдельную инвентаризацию при каждом изменении цифры. Незаполненное поле не должно автоматически означать нулевой остаток. Эти правила нужно подтвердить при возобновлении обсуждения.

Предложено начать с подтверждения менеджером после пересчёта сотрудником. Пользователь пока не выбрал, кто должен окончательно подтверждать отправку.

## 5. Что было проверено по API

Следующие результаты относятся к предыдущей проверке в этом обсуждении; актуальность на дату реализации нужно проверить повторно.

- Ключ `AQSI_API_KEY` уже настроен в проекте; значение ключа в документ не включается.
- Запросы чтения с этим ключом успешно возвращали HTTP 200 для магазинов, товаров, категорий, складов, складских товаров, приёмок и инвентаризаций.
- На момент проверки получены 7 магазинов, 7 складов, 65 товаров, 115 документов приёмки и 180 документов инвентаризации. Это общие количества в аккаунте, не список действующих клубов или напитков.
- Проверено чтение позиций приёмки: товар, количество, закупочная цена и коды маркировки.
- Проверено чтение позиций инвентаризации: товар, количество и коды маркировки.
- Проверено чтение деталей документов, включая склад и статус.
- В спецификации предусмотрено создание инвентаризации с указанием склада и фактических количеств. Ответ создания содержит идентификатор документа; чтение документа возвращает статус `draft` или `complete`.

Основные методы, найденные в спецификации:

| Назначение | Метод |
| --- | --- |
| Список приёмок | `GET /pub/v4/documents/acceptance` |
| Приёмка | `GET /pub/v4/documents/acceptance/{id}` |
| Позиции приёмки | `GET /pub/v4/documents/acceptance/{id}/positions` |
| Создание инвентаризации | `POST /pub/v4/documents/inventory` |
| Список инвентаризаций | `GET /pub/v4/documents/inventory` |
| Инвентаризация | `GET /pub/v4/documents/inventory/{id}` |
| Позиции инвентаризации | `GET /pub/v4/documents/inventory/{id}/positions` |
| Склады | `GET /pub/v4/Warehouses` |
| Товары и сведения об остатках склада | `GET /pub/v4/Warehouses/{id}/goods` |

Создание документов и изменение реального учёта не выполнялись. Наличие метода в спецификации не подтверждает права ключа на запись, успешное проведение документа или изменение остатков.

Дополнительно проверить:

- В каком статусе создаётся инвентаризация и как происходит её проведение.
- Как проверить, что остатки действительно обновлены.
- Возвращает ли API готовые расхождения в количестве и деньгах либо их нужно рассчитывать отдельно; какую стоимость использовать для оценки.
- Как корректно учитывать продажи, происходящие во время пересчёта.
- Как избежать повторного создания документа после тайм-аута или повторного нажатия; наличие поля `externalId` само по себе не доказывает защиту от дублей.
- Требования к маркировке напитков для конкретных позиций и операций.

## 6. Сопоставление с расходниками

Текущий модуль расходников хранит свой каталог, остатки по клубам, категории, фотографии, архив и историю изменений. Изменение количества сейчас обновляет локальную базу; связи с документами aQsi в изученном механизме нет.

Для интеграции требуется согласовать связи:

- клуб Виарыча ↔ магазин и склад aQsi;
- товар расходников ↔ товар aQsi, с учётом вкуса, объёма и единицы измерения.

После сопоставления использовать устойчивые идентификаторы. Похожие названия могут помогать при первоначальном подборе, но не должны быть единственным основанием для изменения учёта.

На первом этапе обсуждались напитки. Прочие расходники предлагалось оставить в существующем процессе; окончательная граница ассортимента ещё не согласована.
